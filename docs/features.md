# Features, in full

Part of the [threers](../README.md) documentation. The README carries a
one-line summary of each of these; this is the long form, and says what the
hard parts were.

- Scene graph (`Object3D`, `Scene`, transforms, layers)
- Buffer geometries, PBR materials, lights, shadows, fog
- **Extended PBR** — clearcoat (direct + IBL), transmission/IOR/dispersion, anisotropy (+rotation), sheen (direct + IBL), thin-film iridescence (+thickness map), volume absorption, normal mapping with vertex tangents, geometric specular AA, and measured-reflectance `materials::presets`
- **HDR pipeline** — `Rgba16Float` textures, float `.hdr` decoding, HDR environment prefiltering, and ACES tone mapping on `Renderer`
- **Area lights** — `RectAreaLight` shading (analytic diffuse form factor + representative-point specular)
- **Custom WGSL materials** via `ShaderMaterial` — a fragment stage, and optionally a vertex stage (`@vertex fn vs_custom`), compiled against the renderer's full preamble: `VsOut`, the frame and mesh uniforms, `sample_env_cube`, `apply_tone_mapping`, `framebuffer_encode` and `standard_vertex`, the built-in transform factored out so a custom stage can start from it. Sixteen `vec4` uniform slots, three storage arrays readable as `s0(i)`/`s1(i)`/`s2(i)` on every backend (a texture where there are no storage buffers), and four textures. `validate()` parses and validates the assembled module with no GPU, naming your own line rather than a position inside seventeen hundred lines of preamble you never wrote. Reachable from JavaScript too, as `THREE.ShaderMaterial` — WGSL rather than GLSL, but the same place in the API. On an `InstancedMesh` it draws every instance (`standard_vertex_instanced` for a custom stage, which takes `InstancedCustomIn`) and reads two per-instance custom columns, `InstancedMesh::set_custom`, as `in.icustom0`/`in.icustom1`. They are vertex attributes, so they work on WebGL2 too `alpha_to_coverage` is three.js's `alphaToCoverage` (`coverage_alpha(c)` in the shader), and a shader can test MSAA samples itself — `THREERS_SAMPLES`, `threers_sample_offset(i)`, returning `frag_out(colour, mask)` — written as `@builtin(sample_mask)` where the backend has it.
- wgpu renderer with post-processing (FXAA, bloom, SSAO, glitch, halftone, …)
- Loaders (glTF, OBJ, STL, PLY, Collada, FBX, HDR, EXR, …), animation, controls, helpers
- **glTF, written as well as read** — `.gltf` and `.glb` out, with the buffers, accessors and material mapping an importer expects, so a scene can make the round trip rather than only arriving. See [glTF](gltf.md).
- **Draco** (`KHR_draco_mesh_compression`) — the compressed-mesh extension decoded in pure Rust: rANS entropy coding, edgebreaker CLERS replayed into a corner table, **both traversals** (standard and the valence-driven one Draco uses above `-cl 7`), attribute seams, and the prediction schemes — difference, parallelogram, constrained multi-parallelogram, geometric normal, portable texture coordinates — with their wrap and canonicalized-octahedral transforms. Verified bit-for-bit against `draco3d`, the encoder that produced the files, rather than against itself: a compressed primitive and its uncompressed twin come out identical index-for-index. See [Draco](draco.md).
- **meshopt** (`EXT_meshopt_compression`) — the other glTF compression, vertex and index codecs both, checked the same way.
- **KTX2 textures** — the container read with its mip chain and supercompression intact, so a block-compressed texture reaches the GPU in the format it was authored in instead of being decoded to RGBA on the way. See [Textures](ktx2.md).
- **Alembic** (`.abc`) — Ogawa archives, the object hierarchy, and `PolyMesh` geometry caches, in pure Rust. See [Alembic](alembic.md).
- **Opt-in WebGL2** (`webgl`) — the same renderer in a browser with no WebGPU. wgpu's GL backend has real limits and the interesting work was finding out which: no compute shaders and no storage buffers, so bloom and ambient occlusion grew raster paths that are each checked against their compute twin to better than a thousandth of a pixel value; sixteen combined texture units rather than per-stage pools, which is what the shader-material binding layout had to be reshaped around. Answered by running headless Chrome rather than by reading the spec: seven tests take a real WebGL2 device, draw lit, skinned and refracting meshes and a full scene, and read the pixels back. See [WebGL2](webgl.md).
- **USD** (`usd`) — `.usda`, `.usdz` and `.usdc`, read **and written** in pure Rust ([below](usd.md))
- **Headless** offscreen render → tightly packed RGBA (`HeadlessRenderer`, native)
- **Render targets** — `Renderer::render_to` into a `RenderTarget`, three.js's `WebGLRenderTarget`: untone-mapped unless it presents, read back in its texture's colour space, and multisampled with `set_samples` (three.js `samples`), colour and depth resolved, independently of the canvas's MSAA
- **Vector SVG export** — `SvgRenderer` draws a `Scene` to an SVG document, one `<path>` per triangle, depth-sorted and lit by the scene's own lights (three.js's `SVGRenderer`). No GPU, no window, no adapter: it runs on the CPU, in CI, over SSH and in a wasm build with no WebGPU. Curved surfaces come out as real Béziers rather than as the polygons they are stored as — measured against an analytic sphere, the outline sits *exactly* on the silhouette from about sixteen segments up. Faces sort by how far back they reach rather than by their centroid, which is what stops a two-triangle floor slicing the bottom off everything standing on it, and geometry is clipped to the frame so the document's bounding box is its canvas. Checked against ray-cast ground truth rather than against another renderer. `svg_from_rgba` wraps an already-rendered frame as an embedded PNG for the cases no per-face sort can express. See [Vector SVG export](svg.md).
- **SVG path data** — `Path`/`Shape` read and write SVG `d` strings with their curves intact: a cubic is one `C`, an ellipse a real `A` arc, and a Catmull-Rom spline converts to cubics exactly rather than being flattened. The reader takes the whole grammar — relative forms, implicit repeats, `S`/`T` reflections, arcs — so SVG artwork can be extruded into geometry, which is what three.js's `SVGLoader` is for. See [SVG path data](svg.md).
- **Opt-in Metal backend** (`metal`, macOS/iOS) — a second renderer that talks to Metal directly through the Objective-C runtime: no `metal-rs`, no `objc` crate, no build script, no new dependency of any kind. Draws the same `Scene` to an offscreen target or a `CAMetalLayer`, and `PassAttachments::from_raw` will draw it into textures your app already owns. wgpu's `Renderer` stays the default and the complete one — see [Metal backend (Apple)](apple-platforms.md) for what this covers and what it does not.
- **Opt-in visionOS** (`visionos`) — the CompositorServices frame loop and ARKit world tracking, again as plain `extern "C"` against the visionOS SDK. Both eyes are drawn in **one pass** into a texture array, depth runs reverse-Z (the only convention the compositor accepts), per-eye projections come from `cp_drawable_compute_projection`, and the device anchor keeps content still in the room instead of riding on the viewer's head. See [visionOS](apple-platforms.md).
- **Video export** (`video`) — frame sequence → ffmpeg; native GIF/APNG/H.264/VP9 when `native-codec` is on
- **Native codecs** (`native-codec`) — pure-Rust APNG, VP9/WebM, H.264/MP4, HEVC/MP4; GIF encode/decode with `gif`; the H.264/HEVC decoders with `video`; wasm-safe browser download
- **Subtitles & captions** — SubRip / WebVTT parse + write, text rasterized on-screen over the 3D frame or burned into exported video, plus sidecar files and soft-subtitle tracks (MP4 `tx3g`, WebM WebVTT). Pure Rust, no font assets required, wasm-safe.
- **Height maps** — `displacementMap` / `displacementScale` / `displacementBias` on Standard and Physical materials, sampled in the vertex stage (plain, skinned, instanced and shadow paths)
- **Kirigami plate lattices** — Kirigami Expanded Miura corrugations (Parra Rubio et al., ASME 2023): planar and curved sandwich cores as plates with crease topology, developed SVG nets, and discrete origami cells. `cargo run --release --example kirigami`
- **Lattice generators** — 35 lattices as `BufferGeometry`, in one API: 8 triply periodic minimal surfaces (gyroid, Schwarz P and D, Neovius, I-WP, Fischer–Koch S, Lidinoid, split P), 7 beam cells (simple cubic, BCC, BCC-Z, FCC, octet truss, diamond, Kelvin), the 9 patterns a slicer draws (rectilinear turning and aligned, grid, triangles, tri-hexagon, honeycomb, cubic, quarter cubic, concentric), 5 face-connected cuboctahedra voxels (rigid, compliant, auxetic, chiral CW/CCW — Jenett et al., Sci. Adv. 2020), and 6 stochastic foams (Voronoi struts and walls, and four classes of spinodal random field — Kumar et al., npj Comput. Mater. 2020). Sized the way a slicer sizes them — ask for *25 % density* and the wall thickness is solved for you — and meshed by a marching cubes that derives its own case table, so ambiguous cells cannot crack and the output is indexed, welded and watertight. `grade` varies thickness across the part, `trim` pours the lattice into any shape you can write as a field, `conform` lays the cells out along a curved part instead of cutting them off at it, and all of it keeps the mesh closed. `metrics` returns the porosity, internal area, pore size, permeability estimate and void connectivity a heat exchanger or a scaffold is specified by; `homogenize`, `conductivity` and `strength` return the cell's effective stiffness tensor, its conductivity (and with it the electrical, diffusive and dielectric answers) and the stress it gives way at, by periodic-boundary FE — on the CPU or, ten times faster and to the same five figures, on a wgpu compute device. `wall_samples` catches the failure mode that would otherwise be silent — a wall thinner than the sample step comes out as gravel, not as a wall — and `resolve_walls` fixes it per generator rather than paying the worst case on all of them. No feature flag, no dependencies.
- **Opt-in planets** (`planet`) — `Planet` / `Starfield` builders that stack a textured body, a cloud shell and an analytically shaded atmosphere; procedural equirectangular map generation; elevation → normal + roughness derivation; and a loader for NASA's public-domain Blue Marble, Black Marble, MODIS, GEBCO, CGI Moon Kit and Deep Star Maps imagery
- **Opt-in path tracer** (`raytrace`) — a physically-based renderer beside the rasteriser, not inside it. Rays leave the camera, scatter off surfaces by their BSDF, and either find a light or die trying; the image is the average of millions of such paths, so global illumination, colour bleeding, soft shadows, glossy interreflection and refraction fall out of the integral rather than being features bolted on. A principled BSDF (Lambert + anisotropic GGX + rough dielectric transmission + clearcoat, with Kulla–Conty energy compensation, so rough gold does not render grey), emissive geometry sampled as area lights, next-event estimation with the power heuristic, **Owen-scrambled Sobol sampling** (every 2D decision a path makes comes from a stratified low-discrepancy pair — 1.5–3× lower RMS error at the same sample count, which is 2–9× the effective samples), **importance-sampled environments** (an HDRI's sun is 6·10⁻⁵ of the sphere — cosine-weighted sampling finds it once in twenty thousand tries and returns speckle), **adaptive sampling** that stops each pixel when its own standard error settles, Russian roulette, Beer–Lambert absorption inside solids, a thin-lens camera with autofocus, and an AOV-guided À-Trous denoiser thresholded on each pixel's *measured* variance, with albedo and normal guides that follow the path through mirrors and glass the way Cycles' do. **Two backends over one scene form**: a portable CPU reference (wasm32 included, rayon-parallel with `parallel`) and a wgpu compute kernel — no new dependency, it reuses the renderer's own wgpu — that runs the same estimator and agrees with the CPU to within Monte-Carlo noise. Takes an ordinary `Scene` with ordinary `Material`s and `Light`s; nothing is authored twice. See [Path tracing](path-tracing.md).
- **Post-processing parameters that work** — twelve public fields across `BloomPass`, `OutlinePass`, `ToneMappingPass` and `FilmPass` were read by nothing: the composer bound a texture and a sampler and each shader hardcoded its constants, so setting one changed the picture not at all. `Pass::uniforms()` carries them now, re-read per frame so `FilmPass::time` makes the grain crawl, and a test moves each of the twelve on its own and asserts the pixels follow.
- **Shared GPU plumbing** — `threers::gpu` (a device with the limits a renderer needs: the main pass declares twenty sampled textures against a downlevel sixteen, and getting that wrong is a validation error from inside wgpu about a layout nobody wrote), `renderer::fullscreen` (targets, ping-pong pairs, the fullscreen-triangle vertex stage, the pipeline-per-format cache, and `Target` — a view bundled with the format and size it does not carry), `renderer::readback` (one half-float decoder and one row-padding fix) and `renderer::colorspace` (the sRGB curve as a WGSL prelude). Not new capability, but a measured deduplication: twelve files had their own fullscreen vertex stage, and **three of the eight half-float decoders were decoding subnormals at a half or a quarter of their value** — one of the eight even carried a comment saying the bug had been found and fixed there. The single implementation is checked against all 65 536 half floats. `postprocessing::DrawPass` completes it at the other end: a composer pass that draws itself, so a simulation joins the chain instead of wrapping it.
- **Opt-in fluid, in two dimensions and three** (`fluid`) — in 3D, `FluidSim3d` carries the same solver through a volume: the stencil grows from five points to seven, vorticity becomes a *vector* so the confinement force becomes the cross product the 2D quarter-turn was standing in for, buoyancy becomes worth having because there is an up, and the volume has to be **ray-marched** because it has no surfaces to draw. The volume lives in a 2D texture with its z-slices tiled across it — a render pass writes one attachment and a 3D attachment is one slice, so a 64³ volume would be eighteen hundred passes a frame — which keeps every stage a single fullscreen pass and keeps the whole thing running on WebGL2. In 2D: an interactive 2D fluid on the GPU: dye poured into a velocity field that is advected, confined, made divergence-free and dissipated sixty times a second, with bloom, sunrays and the dye lit as a height field over the top. A port of Pavel Dobryakov's *WebGL Fluid Simulation* onto wgpu, which is Stam's *Stable Fluids* in the shape GPU Gems 38 gives it: curl, vorticity confinement, divergence, twenty Jacobi sweeps of ∇²p = ∇·u, gradient subtract, and semi-Lagrangian advection of first the velocity and then the ink. Nineteen GLSL programs became one WGSL module with nineteen entry points over a single bind group, and **there is no compute stage in any of it** — so unlike bloom or ambient occlusion it needs no reduced path, and it is the one substantial part of this crate that is *complete* on WebGL2, checked on read-back pixels in headless Chrome. Five named quality levels, two of them past anything the original had (`ultra` carries a 2048-texel dye field, `extreme` 4096) and both clamped to what the device will actually allocate. Beside the original's twenty Jacobi sweeps there is a **multigrid V-cycle** (`PressureSolver::Multigrid`), because the sweeps do not converge: they leave 82 % of a splat's divergence, and sixty-four times as many only reach 24 % — a sweep moves information one texel and the pressure from a localised puff is spread over the whole grid. One V-cycle leaves 0.217 at about three times the default's cost; two reach 0.100. Its smoother is deliberately undamped against the textbook 4/5, because the mode that weighting exists to kill is absent from this right-hand side — the divergence is a two-texel central difference, which has a zero at Nyquist. The other finding worth repeating: the original subtracts **twice** the pressure gradient, the 0.5 that GPU Gems calls `halfrdx` being absent from that one shader — and measured, that is a compensation rather than a mistake. At twenty sweeps the overshoot removes more divergence than the consistent coefficient does (0.654 of it left against 0.825); at three hundred and twenty it leaves the field *more* compressible than not projecting at all (1.269). So it is a knob that belongs with the sweep count, and both halves of that are a test. See [Fluid](fluid.md).
- **Marks** — the data layers a kepler.gl- or Mapbox-style application is built from, as columns uploaded once and drawn in one call each. They include points, wide lines with joins, caps, dashes and great-circle arcs, filled and extruded polygons, instanced shapes, sprites and ground images, labels and icon symbols in single- or multi-channel distance-field text, and heatmaps that can scale to the view. Positions are `f64`, split on the GPU, so data ten million units from zero keeps sub-unit spacing. Filtering and animation run in WGSL hooks, picking reads `(layer, row)` back from an id pass, and labels collide across layers and tiles. `MapView` and `GlobeControls` (which stays exact to a metre off a real planet) drive the camera; `geo` covers Web Mercator, tile pyramids and the globe. The same code runs on WebGPU, WebGL2 and native. See [Marks](marks.md).
- **Reversed depth** (`Renderer::set_reversed_z`) — near maps to 1 and far to 0, which spreads `f32` depth precision almost evenly with distance. That is what planet-scale views need: two walls a metre apart 2 km away stay apart with a 5 cm near plane. Everything that reads depth back follows, from post effects and glass to TAA, ambient occlusion and the composer passes, and each conversion has a test that fails without it.
- **Opt-in mesh BVH** (`mesh-bvh`) — accelerated raycast / shapecast (three-mesh-bvh–compatible)
- **Opt-in CSG** (`bvh-csg`) — boolean ops on `BufferGeometry` (three-bvh-csg–compatible); Rust native + JS addon
- **Opt-in OpenSCAD** (`openscad`) — a `.scad` interpreter **and** a `Solid`/`scad!` Rust DSL, evaluated by a pure-Rust **watertight exact-CSG kernel** (resolves curved∧curved booleans, float fallback where unverifiable). Mesh import/export (STL/OBJ/OFF/3MF/AMF/glTF-GLB, DXF/SVG, `.dat`/`.png` heightmaps) and a live browser playground.
- **Opt-in NURBS** (`nurbs`) — f64 rational curves and surfaces with analytic derivatives, Boehm knot insertion / refinement / Bézier extraction / degree elevation, and **exact** conic and quadric constructors (a circle is a rational quadratic, so a sampled sphere holds its radius to ~1e-15 at any parameter — not to whatever segment count you picked). Curvature-adaptive tessellation to `BufferGeometry` with analytic normals via `NurbsGeometry`, plus JS bindings (`NURBS=1 web/build.sh`). Stage 0 of the B-rep roadmap in [docs/brep-nurbs-plan.md](brep-nurbs-plan.md).
- **Opt-in surface provenance** (`brep`) — every triangle of a built-in primitive knows the analytic `Surface` it was sampled from, so normals come from `Sᵤ × Sᵥ` instead of averaged face normals, UVs come from the surface's own parameterization, and a mesh can be **re-tessellated at any tolerance** after the fact rather than being frozen at whatever `$fn` was chosen. Recovers what triangles cannot hold — a truncated cone's apex is not a vertex, not on any face, and not inside the bounding box. Provenance is a sidecar: it never alters a mesh, and dropping it leaves every consumer behaving as before. Stage 1 of [docs/brep-nurbs-plan.md](brep-nurbs-plan.md).
- **Opt-in analytic CSG acceleration** (`brep-csg`) — when both boolean operands carry provenance, a triangle pair is resolved by asking what its *surfaces* do rather than intersecting the triangles. **Fixes the exact-CSG kernel's longest-standing degeneracy**: two identical primitives translated along a shared axis, which used to fall back to the float kernel and now returns an exact watertight result. The classifier's exact-arithmetic coplanarity test cannot be passed by re-triangulated vertices; surface identity can. Strictly an accelerator — anything without a closed form falls through to the existing path, and a tagged boolean is asserted never to be worse than an untagged one. See [docs/brep-nurbs-plan.md](brep-nurbs-plan.md) § Stage 2.
- **Opt-in B-rep boolean** (`brep-kernel`) — `Body::boolean` for union / difference / intersection on the B-rep itself, not on triangles. Surfaces are intersected in closed form, each face is trimmed by the resulting curves, and the seams become *shared edges*: both sides index the same vertices, so a result is watertight at any tolerance rather than merely coincident — and stays analytic, so a bore comes back as a `Cylinder` you can re-tessellate, not a band of triangles. Coaxial surfaces of revolution are exact, which covers a torus against a cylinder, sphere, cone or another torus — cases with no closed form in general position. A pair with no closed form is *traced* numerically rather than refused, so a cross-drilled hole resolves too. **It declines rather than approximates**: `TangentialContact` where two surfaces touch instead of crossing, `NeedsArrangement` when a face's subdivision does not come apart, `CoincidentFaces` where the two share a surface, and `NotWatertight` if the pieces do not assemble — the layer verifies its own result before returning it, so what you get back is closed or you get nothing. A result is also a *solid*: one closed shell with every edge on exactly two faces, which is what lets it be the input to the next boolean. Stage 4 of [docs/brep-nurbs-plan.md](brep-nurbs-plan.md).
- **Opt-in STEP** (`step`) — ISO 10303-21 read and write, and the AP203/AP214 advanced-B-rep mapping to and from `Body`. Planes, cylinders, spheres, cones and tori map to their own entities, and so do the circles and lines bounding them: a drilled plate arrives in a CAD system as three cylinders it can re-dimension, not as facets it cannot. Import returns a *solid*, so a file you read can be cut again. Export is deterministic — no clock, no hash order — so the same model always produces the same bytes, and anything unmappable is reported rather than silently approximated. The promise is checked, not asserted: a corpus of booleans is written, read back and re-measured, and each must either come back the size it left or have the export name what it could not carry — a face whose edges bound two regions and do not say which (`AmbiguousRegion`), or one bounded partly by its own seam (`SeamBoundary`). Silence *and* a wrong answer is the one outcome ruled out, which is what a format whose point is that the model survives has to guarantee. `cargo run --example brep_part --features step`. Stage 5 of [docs/brep-nurbs-plan.md](brep-nurbs-plan.md).
- **OpenSCAD animation** — the `$t` loop rendered headlessly: colored parts from `color()`, pickable palettes, a camera-relative studio light rig with shadows, a camera that fits or orbits the model (or obeys its `$vpr`/`$vpt`/`$vpd`), static-model caching, concurrent frame evaluation, and one-call PNG / PNG-sequence / video output.
- **Quad and n-gon faces** — `BufferGeometry::polygons` records how many triangles each source polygon became, so a quad stays a quad after loading. Filled by the OBJ, PLY, Collada, FBX, USD and Alembic loaders and kept by `merge_geometries`; wireframes (wgpu, `WireframeGeometry`, SVG) and `EdgesGeometry` draw polygon outlines without the fan diagonals, and USD export writes the polygons back out. `polygon_loop` recovers a polygon's corners from its triangles, however they were triangulated, and returns `None` for holes or interior points. The table is optional and always droppable: `set_index`, or a position write that changes the vertex count, clears it
- **`QuadGeometry`** — a quad from any four corners, not just an axis-aligned rectangle. Subdivided, a non-planar quad becomes a smooth bilinear patch with analytic normals; UVs and vertex order match `PlaneGeometry`, so one swaps for the other. Each cell splits along the diagonal that folds least. Concave quads mesh correctly unsubdivided; bow-ties are unsupported
- **Viewports, scissor and quad view** — `Renderer::set_viewport` / `set_scissor` / `set_scissor_test` / `set_pixel_ratio` / `set_auto_clear` / `clear`, with three.js semantics (bottom-left origin, logical pixels), so several renders can share one target. `helpers::QuadView` lays out top, front and side orthographic panes at one shared scale beside a perspective pane (third-angle, Y-up), with gaps, per-pane backgrounds, a maximise toggle and `pane_at` hit-testing. MSAA works in panes — each is drawn through a pane-sized multisampled target and composited into its rectangle (`auto_clear` off stays single-sampled); TAA and screen-space refraction are off in a sub-rectangle, and post-processing runs over the finished image. Shadow maps are drawn once per quad-view frame and shared by the panes (`shadow_map` `auto_update` / `needs_update`, as in three.js). `QuadViewControls` adds orbit, pan and zoom with one ortho scale and centre shared across the three flat views, double-click maximise and frame-all, wired into `sketch`, `WebQuadView` and the shim's `QuadView.connect(domElement, camera)`. Also on Metal — identical to wgpu, pane for pane, with `MetalViewSurface` for windows (render the panes, then `present()` once) — and on wasm, the three.js shim, Node and Python
- **Companion crate `threers-physics`** — rigid-body physics: gravity, collisions, joints, scene queries (raycast / shapecast), inverse kinematics, continuous collision detection and zero-gravity/orbital models. Pure Rust, wasm-ready, with optional rayon and wgpu-compute acceleration. See [`crates/threers-physics`](../crates/threers-physics).
- **Companion crate `threers-animation`** — easing, tweens, springs, timelines, cinematic camera animation (fly/orbit/paths/shake/shots), and blending an animated pose into a simulated one (ragdolls). See [`crates/threers-animation`](../crates/threers-animation), [`docs/animation.md`](animation.md), and [`docs/camera-animation.md`](camera-animation.md).
- **Published JS package `threers`** — npm / Deno / Node ESM from [`crates/threers-js`](../crates/threers-js). Default **`threers/mini`** (small wasm); **`threers/full`** for CAD/codecs/path tracer. Arch-independent wasm.
- **Published native Node package `threers-node`** — napi-rs addon from [`crates/threers-node`](../crates/threers-node) with per-arch binaries (`@threers/node-darwin-arm64`, …). Not Neon; Deno stays on the wasm package. See [`docs/bindings.md`](bindings.md).
- **Published Python package `threers`** — PyPI wheels from [`crates/threers-py`](../crates/threers-py) (maturin / PyO3; arm64 + x86_64 matrices).
- **Companion crate `threers-robot-arm`** — a four-axis pick-and-place cell run two ways (kinematic and servo-driven), sized from its own inverse dynamics, with a scrubbable browser player. See [`crates/threers-robot-arm`](../crates/threers-robot-arm).
- **Companion crate `threers-probe`** — screen-space neural global illumination from a G-buffer and a set of lighting probes: trained in RLX, run anywhere RLX runs. See [`crates/threers-probe`](../crates/threers-probe).
- **Companion crate `threers-connectome`** — both *Drosophila* connectomes as one node per neuron, 350,033 of them at 60 fps in the browser, with each neuron's `skeleton.swc` fetched and drawn as line segments on click. Reads the `connectome-fs` text trees directly; no dependencies, and none on `threers` either — the renderer runs in the browser as wasm and the Rust side is a reader and a file server. See [`crates/threers-connectome`](../crates/threers-connectome).
- **Companion crate `threers-continuum`** — tendon-driven continuum robots: a flexible rod as a chain of elastic hinges, cable routing, Clark coordinates and task-space tip control. See [`crates/threers-continuum`](../crates/threers-continuum).
- **Opt-in RLX bridge** (`rlx`) — [RLX](https://crates.io/crates/rlx), an ML compiler + runtime, as a neighbour of the renderer rather than a layer under it. Vertex attributes and pixels convert to `rlx` tensors of a declared shape and back (NHWC/NCHW, sRGB↔linear, `Rgba16Float` included), and `GraphRunner` compiles a graph once so a per-frame filter does not pay the compiler sixty times a second. On top of that: `ConvFilter` (blur/sharpen/Sobel/emboss as depthwise conv2d), `Diffusion` (iterated `h ← h + κ∇²h` for terrain), `mesh::taubin_smooth` (smoothing as a graph over `[n, 3]` positions), `ColorGrade` (a colour transform **fitted** to a reference by autodiff — not applied, *learned*), and `Palette` (k-means with the assignment step on the device). Built with rlx's `cpu`, `tensor` and `gpu` backends, native **and** wasm32.
- **Delaunay / convex hull / Voronoi, built in** — `math::delaunay`, `math::convex_hull` and `math::voronoi_cells`, in floating point and with no feature flag, because a scattered set of points is the most common input in generative work. Deliberately **no super-triangle**: the usual trick of wrapping the input in one huge triangle and discarding whatever still touches it quietly loses thin triangles along the hull, whose circumcircles are enormous — a chord of 3 with a sagitta of 0.004 gives a radius of 271 — so a super-triangle vertex at any finite distance eventually lands inside one and the result is a crack between the triangulation and its own hull. Insertion starts from a real triangle and extends the mesh across the hull edges each new point can see. The test that matters is area: the mesh was *consistent* with the bug in place, and only comparing the triangles' area against the hull polygon's showed it. For input that is near-degenerate on purpose, the exact predicates below are still the ones to reach for
- **Opt-in exact Delaunay / Voronoi** (`rlx-geo`) — [`rlx-geo`](https://crates.io/crates/rlx-geo)'s integer predicates, so scattered samples triangulate to *the* Delaunay mesh rather than one a floating-point predicate rounded into a near-miss (a flipped triangle in a height field is a visible spike). `heightfield_geometry` returns `BufferGeometry` with normals and UVs; `refine_heightfield` samples adaptively, reaching ~9× lower error than a uniform grid of the same vertex count; Voronoi labels, site-distance, wall-distance and edge maps drive cell textures (cracked mud, stained glass) via `normal_map_from_height`.
- **Parallel CPU work** (`parallel`) — rayon-backed BVH/CSG evaluation; native only, and order-preserving so results are unchanged
- **Web**: `web/threejs-shim.js` + wasm — drop-in `THREE.*` replacement targeting three.js r165
- **Native**: winit examples for desktop development and debugging
- **Creative coding** — the things d3 and p5 have that a renderer usually makes you write again. `sketch(options, setup)` is a window, a scene, a camera, a renderer and a loop in one call, where the shortest path from nothing to a moving picture used to be eighty lines of adapter, device, surface and event `match`; `setup` returns the draw closure, so whatever setup built is simply captured. `overlay::Overlay` is immediate-mode 2D over the top — `rect`, `circle`, `line`, `polygon`, `text`, with sticky `fill`/`stroke` — every primitive a signed distance function so they all anti-alias through one rasteriser, and compositing in linear light, which is what keeps anti-aliased edges from fringing dark. `Camera::world_to_screen` puts a label where an object is, and returns `None` behind the eye rather than a plausible wrong answer. Plus a seeded `Rng`, `ColorRamp` (viridis, magma, inferno, plasma, turbo, cool-warm, interpolated through OkLab), d3-scale's `map_range` / `ScaleLinear` / `ScaleLog` / `ScalePow` / `ticks`, `Easing` moved down from `threers-animation` where `cargo add threers` could not see it, and curl, fbm, ridged and turbulence noise on `SimplexNoise`. `cargo run --release --example sketch_flow`, `--example sketch_labels`
